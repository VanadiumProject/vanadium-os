# Vanadium Execution Model

The Vanadium Console architecture uses a **Tri-Processor Asynchronous Model**. This separates the system's core responsibilities into independent hardware domains, coordinated via a shared memory space and hardware interrupts.

## 1. The Three Processors

| Processor | Chip | Primary Responsibility |
| :--- | :--- | :--- |
| **Main CPU** | CH32V307 | Game logic, input handling, memory management, and overall system orchestration. |
| **PGPU** | CH32V307 | Frame buffer rendering, sprite compositing, palette manipulation, and geometry calculation. |
| **APU** | CH32V003 | Procedural audio synthesis, sample playback, and mixing. |

## 2. Communication Strategy

### Command Queues (Asynchronous)
Instead of the Main CPU waiting for the PGPU or APU to finish a task, it uses **Lock-Free Command Queues** in shared SRAM.
- **Main CPU:** Pushes drawing or sound commands onto the queue.
- **PGPU/APU:** Polls its respective queue and executes the commands.
- **Feedback:** The PGPU/APU updates status flags in the **Shared Control Block** to signal readiness or completion.

### Synchronization (VBLANK)
The Main CPU synchronizes its logic loop to the **Vertical Blanking (VBLANK)** signal generated by the display controller (managed by the PGPU).
- On VBLANK interrupt, the Main CPU:
  1. Updates the Shared Control Block with the next frame's base addresses.
  2. Processes input.
  3. Executes one frame of game logic.
  4. Flushes drawing commands to the PGPU queue.

## 3. Kernel vs. Application Execution

The Vanadium OS follows a **Micro-Kernel approach** for games:
- **During Shell Mode:** The Main CPU runs the full OS, managing windowing and resource allocation for the graphical shell.
- **During Game Mode:** The Main CPU yields almost all control to the game binary. The OS stays resident in a tiny memory footprint (< 2 KB) to handle only the most essential hardware interrupts and cartridge I/O.

## 4. Why Three CPUs?
1. **Determinism:** Game logic (Main CPU) is never interrupted by heavy rendering tasks (PGPU).
2. **Simplified Programming:** Developers can treat the PGPU as a dedicated hardware graphics accelerator rather than having to interleave rendering and logic.
3. **Power Efficiency:** Independent units can be clocked differently or put into low-power modes when not needed.
